## 1. 产品定义

### 1.1 一句话定义

**"把产品经理的需求变成可上线产品的AI全自动交付平台。"**

PM用业务语言描述需求，AI全自动完成设计、编码、测试、部署。PM通过可视化进度和引导式验收全程掌控，从"我想要一个电商系统"到"系统已上线"，PM只需要5次交互、约30-70分钟参与时间。

与传统开发流程的对比：

| 维度 | 传统开发 | MIXIA Builder |
|------|---------|---------------|
| 从需求到上线 | 数周至数月 | 72-175分钟 |
| PM需要理解的技术概念 | 数据库、API、前端框架、CI/CD... | 无——全部由AI处理 |
| PM的核心动作 | 写PRD、跟进开发、验收测试、协调部署 | 描述需求、确认方案、看截图答是否、点发布 |
| 沟通成本 | PM与开发者反复对齐理解 | PM直接与AI对话，AI复述确认 |
| 修改成本 | 需求变更流程、重新排期 | 告诉AI"这里不对"，分钟级修复 |

### 1.2 核心设计原则

以下5条原则是MIXIA Builder所有产品决策的最高准则。当任何功能设计产生分歧时，以这5条原则为裁决依据：

**原则1：以完美做出整个项目为核心目标**

不做原型、不做demo、不做"看起来像那么回事"的半成品。目标是生成可上线的完整产品——前端页面、后端API、数据库、用户认证、支付接入、部署配置，一个都不少。

这意味着：
- 代码质量必须达到生产标准（有测试、有安全扫描、有性能基线）
- 不允许用TODO注释搪塞——每个功能都必须完整实现
- 部署链路完整——PM点"发布"后，用户真的能通过URL访问

**原则2：PM视角是交互层，底层工程级完整**

PM看到的是简洁的功能地图、直观的进度条、清晰的截图对比。但底层运行着完整的工程流程：代码lint、类型检查、安全扫描、单元测试、集成测试、E2E测试、性能基线检测——全部自动执行，PM不需要看到、不需要理解、不需要操作。

类比：PM是飞机乘客，看到的是航班信息和登机口。底层的飞行计划、气象分析、引擎检查、航线协调全部由系统自动完成。

**原则3：凡PM不会的，AI 100%自动代替**

PM不会写代码——AI写。PM不会写测试——AI写。PM不会配置CI/CD——AI配。PM不会做安全扫描——AI做。PM不会部署服务器——AI部署。

唯一需要PM做的事：描述业务需求、确认功能方案、判断"这个对不对"。这些是PM的专业领域，不应由AI代替。

**原则4：无法自动化的，一步步引导PM**

有些事AI无法独立判断——"登录页的视觉风格你喜欢吗？"、"这个业务流程符合你的预期吗？"这些需要PM的主观判断。

对于这类场景，系统不会给PM一个空白输入框让PM自己想怎么描述。而是：
- 给PM看截图，问"是/否"
- 给PM选择题，而非填空题
- PM说"不对"时，AI追问结构化问题定位具体问题
- PM说"说不清楚"时，引导PM截图或录屏

**原则5：用户交互最小化**

PM总参与度约15%，集中在"看图确认"和"点发布"两种动作。其余85%的时间，PM可以做别的事。

量化目标：
- PM核心交互次数：5次（需求描述、方案确认、UI确认、引导式验收、上线确认）
- PM总参与时间：30-70分钟（中等项目，约20页面/50个API）
- 任何单次交互不超过30分钟

### 1.3 目标用户画像

#### 主要目标用户：产品经理（PM）

| 特征 | 描述 |
|------|------|
| 角色 | 产品经理、产品负责人、项目经理 |
| 技术能力 | 懂业务逻辑和产品流程，不会编码，不理解数据库、API等技术概念 |
| 核心痛点 | 有产品想法但无法独立实现；现有AI Agent是黑箱——不知道AI写了什么、逻辑对不对、哪里需要改 |
| 日常工具 | Jira/飞书（项目管理）、Figma（设计）、Notion（文档）、企业微信/Slack（沟通） |
| 付费能力 | 企业SaaS预算，个人$15-100/月 |
| 使用场景 | 需要快速搭建内部工具、MVP验证、产品原型、小型完整产品 |

#### 次要目标用户

| 用户群 | 典型画像 | 使用场景 |
|--------|---------|---------|
| 创业者 | 有商业想法、无技术团队 | 快速验证MVP，省去招聘开发者的时间和成本 |
| 运营人员 | 需要简单的数据面板、活动页面 | 自助创建运营工具，不再等排期 |
| 设计师 | 有完整UI设计，想看到可交互的实现效果 | 将Figma设计稿变成可运行的前端 |
| 技术PM | 懂一些代码但不想亲自写 | 快速生成项目骨架，再交给开发团队微调 |

#### 明确不是目标用户

| 用户群 | 原因 | 推荐替代工具 |
|--------|------|-------------|
| 专业开发者（日常写代码） | 他们需要的是代码补全、代码审查，不是项目生成 | Cursor、Copilot、Windsurf |
| 已有大型项目的团队 | 本产品专注"从0到1"，不做"已有项目优化" | Cursor、Devin |
| 需要高度定制UI的设计团队 | 本产品的UI是AI生成的，无法做到像素级定制 | Figma + 前端开发 |

### 1.4 市场定位（竞品空白分析）

#### 一句话市场定位

**"面向PM的AI全自动项目交付平台"** —— Plan-First（先规划、再执行）范式的开创者。

#### 竞品格局与空白地带

当前AI编程工具市场分为四个象限：

```
                    面向开发者
                       ↑
                       │
         Cursor    │    Devin
         Copilot   │    OpenHands
         Windsurf  │    
  ─────────────────┼──────────────→
  代码补全/         │         全自动
  辅助编码          │         Agent
                   │
         Bolt.new  │   ★ MIXIA Builder
         Lovable   │   （空白地带）
         v0        │
                   │
                   ↓
                面向非技术用户
```

**左上象限（代码补全）：** Cursor、Copilot、Windsurf、通义灵码、Trae。面向开发者，在已有代码上做补全和修改。PM完全用不了。

**右上象限（AI Agent）：** Devin、OpenHands。全自动写代码，但是黑箱——PM不知道AI在干什么、干了什么、对不对。

**左下象限（快速原型）：** Bolt.new、Lovable、v0。非技术用户可以"说一句话"生成页面。但生成的是原型而非完整产品，且无法精细控制。

**右下象限（空白）：** 面向非技术用户 + 全自动 + 白箱可控 + 完整项目交付。这是MIXIA Builder的定位。

#### 与关键竞品的详细对比

**vs. Lovable（最接近的竞品）**

Lovable在2026年2月推出了Plan Mode——AI编码前先展示计划供用户审查。这与MIXIA Builder的Plan-First范式有部分重合。但Lovable的Plan Mode存在以下局限：

| 维度 | Lovable | MIXIA Builder |
|------|---------|---------------|
| 计划形式 | 文本列表（"创建登录页"级别） | 可视化功能地图（DAG图） |
| 粒度 | 粗（文件级） | 细（字段级业务逻辑） |
| 依赖可视化 | 无 | 功能间依赖关系一目了然 |
| 影响分析 | 无 | 修改一个功能自动分析影响范围 |
| 多方案对比 | 无 | AI可生成多个方案供PM选择 |
| 成本预估 | 无（按消息收费，不透明） | 生成前预估、生成中实时显示 |
| 测试保障 | 单层（AI生成+执行） | 三层防线（同源自测+交叉验证+PM验收） |
| 部署 | 内置（仅Supabase） | 多平台自动部署 |
| 大项目可靠性 | 20-30文件后急剧下降 | Validate-Before-Propagate阻断错误传播 |

Lovable的8大已知踩坑（我们需要避免）：
1. 开源到商业化的过渡引发社区抵触
2. 只支持React+Supabase限制用户群
3. 按消息计费不透明引发大量抱怨
4. 大项目（20-30文件后）可靠性急剧下降
5. 非技术用户期望过高（"说一句话就完美"）
6. 切换AI模型导致代码风格波动
7. 品牌更名（GPT Engineer -> Lovable）短期SEO受损
8. AI声称改好了实际引入新问题（幻觉）

**vs. Devin 2.0**

Devin是"全自动AI开发者"，2026年从$500/月降至$20/月。核心区别在于Devin是黑箱——PM无法理解AI在做什么。

| 维度 | Devin | MIXIA Builder |
|------|-------|---------------|
| 透明度 | 黑箱——PM看不懂终端命令和代码diff | 白箱——PM看到功能地图和截图 |
| 控制力 | 只能给指令，无法指定"只改这个功能" | 功能级精细控制 |
| 验收方式 | PM需要理解代码 | 截图+是否题 |
| 目标用户 | 开发者（PM用不了） | PM |

**vs. Bolt.new / v0**

快速原型工具，PM可以用，但产出的是原型而非完整产品。

| 维度 | Bolt.new / v0 | MIXIA Builder |
|------|---------------|---------------|
| 产出质量 | 原型级（无测试、无安全、无后端逻辑） | 生产级（完整测试+安全+部署） |
| 项目规模 | 单页面/简单应用 | 20+页面/50+API的完整系统 |
| 修改方式 | 重新描述需求（无增量修改） | 功能级增量修改+影响分析 |
| 部署 | 无或手动 | 一键自动部署 |

#### 核心差异化总结

**市面上没有任何产品同时具备以下全部能力：**

1. **可视化功能地图** —— PM用业务语言看到功能间的依赖关系
2. **功能地图驱动代码生成** —— 不是文本列表，是可交互的可视化方案图
3. **逐功能执行+状态追踪** —— PM实时看到每个功能的进度
4. **三层AI测试防线** —— 同源自测+交叉验证+PM引导验收，阻断幻觉
5. **引导式验收** —— PM不需要看代码，通过截图和是否题验收
6. **一键自动部署** —— PM点"发布"，系统自动完成从构建到上线的全部流程
7. **业务翻译层** —— AI内部的技术操作自动翻译为PM能理解的业务语言

### 1.5 产品能力边界（明确能做什么、不能做什么）

清晰的能力边界是管理PM期望的关键。过高的期望是同类产品（Lovable、Devin）用户流失的首要原因。

#### 能做什么（核心能力）

| 能力 | 说明 | 举例 |
|------|------|------|
| **从0到1创建完整Web应用** | 前端+后端+数据库+认证+支付+部署 | 电商系统、SaaS后台、内部工具 |
| **标准CRUD应用** | 数据的增删改查+列表+详情+搜索+筛选 | 会员管理系统、订单管理、库存管理 |
| **用户系统** | 注册、登录、密码找回、个人信息、权限 | 任何需要用户账号的产品 |
| **支付集成** | 接入微信支付、支付宝、Stripe等 | 电商、SaaS订阅、知识付费 |
| **数据面板** | 图表+统计+报表+导出 | 运营数据看板、KPI面板 |
| **多页面应用** | 20+页面的完整应用，带路由和导航 | 企业内部管理系统 |
| **响应式布局** | 自动适配桌面和移动端 | 所有Web应用 |
| **第三方服务对接** | 邮件、短信、OSS存储、OAuth登录 | 通知系统、文件上传 |
| **全自动测试** | 单元测试+集成测试+E2E测试+安全扫描 | 所有项目（不需要PM操作） |
| **一键部署** | 自动构建、部署到云端、配置域名 | 所有项目 |

#### 不能做什么（明确边界）

| 不能做的事 | 原因 | 替代方案 |
|-----------|------|---------|
| **像素级UI还原** | AI生成的UI会接近但不能100%还原设计稿 | 生成后交给前端微调，或使用Figma |
| **高复杂度算法** | 机器学习模型、金融量化策略、实时3D渲染 | 交给专业开发团队 |
| **已有项目的代码修改** | 本产品专注"从0到1"，不做已有代码库的理解和修改 | 使用Cursor/Copilot |
| **原生移动App（iOS/Android）** | 当前仅支持Web应用（包括移动端响应式网页） | 后续版本考虑React Native |
| **超大规模系统** | 微服务架构、分布式系统、高并发优化 | 需要专业架构师 |
| **硬件相关开发** | 嵌入式、IoT、驱动程序 | 不在产品范围内 |
| **合规认证** | 等保三级、HIPAA、SOC2等合规审计 | 需要专业合规团队 |

#### 灰色地带（能做但有限制）

| 场景 | 限制 | PM需知 |
|------|------|--------|
| **复杂业务逻辑** | 超过5层嵌套的条件判断可能不准确 | 验收时重点检查复杂逻辑 |
| **多角色权限系统** | 支持基础RBAC，不支持动态策略引擎 | 超过10种角色时建议拆分 |
| **实时功能** | 支持WebSocket基础通信，不支持高频实时同步 | 聊天可以，协同编辑不行 |
| **国际化（i18n）** | 支持多语言框架，但翻译质量取决于AI | 关键翻译需人工校对 |
| **SEO优化** | 支持基础SSR/SSG，不做深度SEO策略 | 营销型网站需额外SEO工作 |

## 2. 用户交互设计

### 2.1 PM的5次核心交互（I1-I5）

从"描述需求"到"项目上线"，PM最少只需要5次交互。以下是每次交互的定义、目标和约束：

| 编号 | 交互名称 | PM的动作 | 预计时间 | 能否省略 | 核心目标 |
|------|---------|---------|---------|---------|---------|
| **I1** | 需求描述 | 用自然语言描述想要什么产品 | 5-15分钟 | 不可省略 | 让AI理解PM想要什么 |
| **I2** | 方案确认 | AI生成功能地图+技术方案，PM确认或提出修改 | 10-20分钟 | 不可省略 | 确保AI的理解与PM预期一致 |
| **I3** | UI审美确认 | AI生成页面截图/原型，PM确认视觉风格 | 3-5分钟 | 可与I2合并 | 避免功能做完后PM说"不好看" |
| **I4** | 引导式验收 | 系统引导PM逐功能看截图答是/否 | 10-30分钟 | 不可省略 | PM确认功能正确性 |
| **I5** | 上线确认 | AI展示部署清单，PM说"go" | 1分钟 | 不可省略 | PM授权正式上线 |

**总PM参与时间：约30-70分钟。** I1和I2之间、I2和I4之间，AI在后台自动工作（代码生成、测试、部署预览），PM可以去做其他事情。

交互时间线：
```
|──I1──|          |──I2──|        |I3|                     |──I4──|   |I5|
  PM    ← AI工作 →  PM   ← AI工作 → PM  ← AI全自动工作 →    PM     PM
  在场    5-15分钟   在场   5-15分钟  在场   12-35分钟       在场    在场
```

### 2.2 每次交互的详细UX设计

#### I1: 需求描述（PM的第一次输入）

**目标：** PM用自己的语言描述想要什么，AI通过追问把模糊需求变成结构化定义。

**入口界面：**

PM打开MIXIA Builder后看到的第一个页面：

```
┌────────────────────────────────────────────────┐
│                                                │
│           描述你的产品想法                      │
│                                                │
│  ┌──────────────────────────────────────────┐  │
│  │                                          │  │
│  │  例如：                                   │  │
│  │  "我想做一个宠物寄养平台，                │  │
│  │   宠物主人可以发布寄养需求，              │  │
│  │   寄养家庭可以接单，                      │  │
│  │   支持在线支付和评价。"                   │  │
│  │                                          │  │
│  └──────────────────────────────────────────┘  │
│                                                │
│  或从模板开始：                                │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐         │
│  │ 电商  │ │ SaaS │ │ 后台  │ │ 更多  │         │
│  │ 系统  │ │ 产品  │ │ 管理  │ │ 模板  │         │
│  └──────┘ └──────┘ └──────┘ └──────┘         │
│                                                │
└────────────────────────────────────────────────┘
```

**AI追问流程（需求澄清对话）：**

PM输入需求后，AI不会立即生成方案。而是进入需求澄清阶段，追问关键信息。追问遵循"选择题优先"原则——每个问题给出具体选项，PM只需点选。

追问的核心维度：

| 追问维度 | 为什么要问 | 示例选项 |
|---------|-----------|---------|
| 用户角色 | 确定需要多少种角色和权限 | "管理员+普通用户" / "管理员+商家+买家" / 自定义 |
| 核心流程 | 确定主要业务路径 | "注册→浏览→下单→支付→评价" / 自定义 |
| 数据实体 | 确定需要管理什么数据 | "用户+商品+订单" / "用户+文章+评论" / 自定义 |
| 第三方对接 | 确定需要哪些外部服务 | "微信支付" / "支付宝" / "邮件通知" / "短信" / 不需要 |
| UI风格 | 确定视觉基调 | "简约商务" / "温暖亲切" / "科技感" / "参考某网站" |
| 规模预期 | 影响架构和成本决策 | "个人/团队内部使用" / "面向公众，预期千级用户" / "大规模" |

追问示例对话：

```
AI: 你提到了宠物寄养平台。我需要确认几个关键信息：

1. 需要哪些用户角色？
   A) 宠物主人 + 寄养家庭（两种角色）
   B) 宠物主人 + 寄养家庭 + 平台管理员（三种角色）
   C) 其他（请补充）

PM: B

AI: 好的，三种角色。支付方式需要哪些？
   A) 微信支付
   B) 支付宝
   C) 微信支付 + 支付宝
   D) 暂不需要线上支付

PM: C

AI: 收到。最后一个问题——寄养家庭需要认证吗？
   A) 需要实名认证（上传身份证）
   B) 只需要填写基本信息
   C) 需要平台人工审核

PM: A
```

**追问完成标准：**

AI在内部维护一个"需求完整度"评分（PM不可见）。当以下条件全部满足时，AI停止追问并进入方案生成：

- 用户角色和权限明确
- 核心业务流程明确
- 数据实体和关键字段明确
- 第三方服务需求明确
- 不存在逻辑矛盾（如"无需登录但需要个人中心"）

**追问轮次限制：** 最多5轮追问。超过5轮时AI综合已有信息生成方案，将不确定的部分标记为"AI假设，待PM确认"。

**核心设计：方案讨论是无限轮次的迭代循环**

I2不是一次性的"展示→确认"，而是**PM和AI之间的持续对话**。PM可以反复讨论、提问、修改、推翻、重来，直到完全满意为止。AI必须保持耐心，不催促PM确认，不暗示"差不多可以了"。

```
┌─────────────────────────────────────────────────────────┐
│                 I2 方案讨论迭代循环                        │
│                                                         │
│  AI展示功能地图                                          │
│       ↓                                                 │
│  PM查看 ──→ PM满意 ──→ 点"确认方案" ──→ 进入代码生成     │
│       │                                                 │
│       └──→ PM不满意 ──→ 继续讨论 ──→ AI更新地图          │
│                             ↑              │             │
│                             └──────────────┘             │
│                          （无限循环，直到PM满意）          │
│                                                         │
│  每轮讨论中PM可以：                                       │
│  · 提问："为什么这里需要一个单独的模块？"                   │
│  · 挑战："我觉得不需要这么复杂"                            │
│  · 修改："把登录改成微信扫码登录"                          │
│  · 重来："这个方案不行，换个思路"                          │
│  · 对比："能不能给我两个方案选？"                          │
│                                                         │
│  AI的行为原则：                                          │
│  · 永远不主动建议"差不多可以确认了"                        │
│  · 每次修改后完整展示更新后的功能地图                      │
│  · 修改时先确认范围（局部/全局），再执行                    │
│  · 记住所有讨论历史，不重复之前确认过的问题                 │
└─────────────────────────────────────────────────────────┘
```

**AI耐心原则（强制约束）：**

AI在I2阶段的system prompt中注入以下硬性约束：

```
[I2_PATIENCE_RULES]
1. 不主动催促确认。不说"方案已经比较完善了，可以确认了吗？"
2. 每次PM提出修改，先说"好的"再执行，不说"这样改的话会增加复杂度"来暗示PM别改
3. PM第10次修改和第1次修改得到同等质量的回应
4. 如果PM说"我再想想"，回复"没问题，想好了随时告诉我"，不追问
5. PM可以推翻之前确认过的决定（"之前说的认证方式我改主意了"），AI不抱怨
6. 讨论中PM问"你觉得呢？"时，给出专业建议但最终尊重PM决定
```

**关联节点检测的技术规则：**

AI在执行局部修改时，自动检测以下4类关联：

| 关联类型 | 检测规则 | 示例 |
|---------|---------|------|
| **数据依赖** | 被修改节点的输出数据被其他节点使用 | 修改"用户表"→ 影响所有读取用户信息的模块 |
| **流程依赖** | 被修改节点是其他节点的前置步骤 | 修改"登录方式"→ 影响所有需要登录态的功能 |
| **共享组件** | 被修改节点使用的组件也被其他节点使用 | 修改"短信验证"→ 影响注册和忘记密码两个功能 |
| **业务规则** | 被修改的业务规则在其他节点中也生效 | 修改"退款规则"→ 影响订单管理和财务报表 |

检测结果分为三级：

| 级别 | 含义 | AI的处理 |
|------|------|---------|
| 🔴 **必须同步修改** | 不修改会导致功能断裂 | 自动包含在修改方案中，PM必须确认 |
| 🟡 **建议同步修改** | 不修改不会报错但逻辑不一致 | 展示建议，PM可选择是否一起改 |
| 🟢 **无需修改** | 完全独立，不受影响 | 不展示（默认折叠，可展开查看） |

- 预览环境保持运行，不受影响

### 2.3 PM反馈解析机制

PM不是开发者，给不了精确的技术描述。MIXIA Builder的反馈解析机制专门为"非精确反馈"设计。

#### 核心原则：选择题优先 + 截图兜底 + AI复述确认

**层级1：选择题优先**

PM的任何反馈，系统第一反应是给出选择题而非让PM自由描述。

```
PM: "注册流程太复杂"

AI:（不猜PM的意思，给出选择题）
可以通过以下方式简化：
   A) 减少必填字段：只保留邮箱+密码
   B) 分步注册：第一步只填邮箱密码，成功后再补充
   C) 添加第三方登录：微信一键登录
   D) 以上都不是，我具体说

PM: A
```

**层级2：截图兜底**

当PM选了"以上都不是"或说"不对但说不清楚"时，引导PM截图或录屏——比文字描述快10倍、准10倍。

```
PM: "这个页面不太对"

AI: 哪里不对呢？
   A) 页面布局有问题
   B) 功能不工作
   C) 数据显示不对
   D) 我说不清楚

PM: D

AI: 没关系！截个图标注一下哪里不对？
    [上传截图]  或  [录制屏幕10秒]
```

**层级3：AI复述确认**

AI收到反馈后，不立即动手修改。先用结构化格式复述理解，让PM确认——避免AI理解错误导致白改。

```
AI: 我理解的问题：
   📍 位置：登录页 → 密码输入框
   🔴 现状：没有显示/隐藏切换
   🟢 期望：加一个眼睛图标切换密码可见性

   理解正确吗？  [是，去修]  [不对，我再说]
```

#### 反馈类型分类与处理策略

| 反馈类型 | PM的典型表述 | 系统处理方式 |
|---------|-------------|-------------|
| 明确指令 | "把按钮颜色改成蓝色" | 直接执行，执行后展示对比截图 |
| 模糊不满 | "这个看起来不太对" | 选择题引导 → 截图兜底 |
| 逻辑修改 | "注册时应该先验证手机号" | AI展示修改方案 + 影响分析 → PM确认 |
| 新增需求 | "还需要一个导出Excel功能" | AI评估工作量 + 更新功能地图 → PM确认 |
| 删除需求 | "评论功能不要了" | AI展示影响分析（哪些功能受影响）→ PM确认 |
| 矛盾修改 | "不需要登录，但要有个人中心" | AI指出矛盾，给出解决选项 |

#### 反馈迭代限制

每个功能节点的修改有迭代限制（3轮升级机制，详见第8章）：
- 第1轮修改：AI自动修复 + 重新截图确认
- 第2轮修改：AI尝试不同策略修复
- 第3轮修改：如果仍不满足，自动升级处理方式——"这个问题比预期复杂，建议截图标注具体问题"或标记为"需要技术支持"

| **失败场景** | PM需求过于模糊（AI追问5轮仍不清晰）→ 提示PM补充更多信息 |

**Phase 1内部流程：**

```
PM输入需求
    ↓
AI解析关键词 → 识别产品类型（电商/SaaS/内部工具/...）
    ↓

    ↓ (不完整)

    ↓
PM确认/修改
    ↓ (确认)

```

#### Phase 2: 代码生成

| 项目 | 说明 |
|------|------|
| **输入** | PM确认的功能地图 + 项目配置（技术栈、UI风格） |
| **输出** | 完整的项目代码（前端+后端+数据库+配置） |
| **PM参与度** | 0%——全自动 |
| **耗时** | 5-15分钟（中等项目） |
| **自动化部分** | 拓扑排序 → 逐节点代码生成 → 上下文传递 → 节点验证 |
| **PM可见内容** | 实时进度条（"正在创建用户系统...3/8完成"） |
| **失败场景** | 单节点失败 → AI自动重试（最多3次）→ 仍失败则跳过+标记 |

**Phase 2的关键机制：**

1. **拓扑排序执行：** 根据功能间的依赖关系确定生成顺序。无依赖关系的功能可并行生成。

2. **Validate-Before-Propagate（验证先于传播）：** 每个功能节点生成代码后，先执行验证（语法检查+依赖验证），验证通过后才将输出传递给下游节点。这是阻断AI幻觉级联传播的核心机制。

3. **上下文分层传递：**
   - 直接依赖的功能：传递完整输出
   - 间接依赖的功能（2-3层）：传递AI摘要
   - 更远的功能：仅传递元数据
   - 全局上下文：技术栈声明 + 编码规范

4. **自动添加测试锚点：** 每个前端组件自动添加`data-testid`属性，为后续E2E测试做准备。

5. **代码后处理：** 每个节点生成代码后自动执行格式化（Prettier/Black）→ Lint修复（ESLint --fix）→ import排序。不依赖AI保证代码风格一致，靠工具强制统一。

#### Phase 3: 质量关卡

| 项目 | 说明 |
|------|------|
| **输入** | Phase 2生成的完整项目代码 |
| **输出** | 通过质量检查的代码（或标记了问题的代码） |
| **PM参与度** | 0%——全自动 |
| **耗时** | 1-3分钟 |
| **自动化部分** | Lint + 类型检查 + 安全扫描 + 依赖验证 + 死代码检测 |
| **PM可见内容** | 无（PM不需要知道这个阶段存在） |
| **失败场景** | 检查项失败 → AI自动修复 → 重跑 → 3次失败暂停报告 |

**Phase 3检查清单：**

| 检查项 | 工具 | AI自动修复能力 | 修复方式 |
|--------|------|-------------|---------|
| 代码格式 | ESLint + Prettier | 95% | `eslint --fix` + `prettier --write` |
| 类型安全 | TypeScript tsc | 80% | AI读错误信息 → 修改代码 |
| 安全漏洞 | npm audit + Semgrep | 中低危70%，高危需人工 | AI应用已知修复模式 |
| 依赖验证 | npm/pypi registry API | 100% | 替换为真实存在的包+最新稳定版本 |
| 死代码 | 静态分析 | 90% | 删除未使用的导入和变量 |
| Secret检测 | 正则扫描 | 100% | 移除硬编码的密钥和token |

#### Phase 4: 测试（详细设计见第7章）

| 项目 | 说明 |
|------|------|
| **输入** | Phase 3通过质量检查的代码 |
| **输出** | 测试报告（覆盖率、通过/失败、修复记录） |
| **PM参与度** | 0%——全自动 |
| **耗时** | 5-15分钟 |
| **自动化部分** | 三层测试防线（同源自测+交叉验证+属性/变异测试） |
| **PM可见内容** | 无（PM不需要知道测试细节） |
| **失败场景** | AI分析失败原因 → 修改代码或测试 → 重跑 → 上限后暂停 |

**三层防线概述：**

| 层 | 做什么 | 可靠性 | 成本 | 重试上限 |
|----|--------|--------|------|---------|
| Layer 1: 同源自测 | 同一AI生成代码后生成测试并执行 | 75% | 低 | 3次 |
| Layer 2: 交叉验证 | 不同AI从PM需求（非代码）独立生成测试 | +13% → 88% | 中 | 2次 |
| Layer 3: 属性/变异测试 | 验证测试本身的质量 | +7% → 95% | 中 | 1次 |

详细设计见第7章。

#### Phase 5: 自动部署到Preview

| 项目 | 说明 |
|------|------|
| **输入** | Phase 4通过测试的代码 |
| **输出** | 可访问的预览URL + 关键页面截图 |
| **PM参与度** | 0%——全自动 |
| **耗时** | 1-2分钟 |
| **自动化部分** | 构建 → 部署到预览环境 → 冒烟测试 → 截图生成 |
| **PM可见内容** | 无（Phase 6开始时PM才看到预览结果） |
| **失败场景** | 构建失败 → AI分析修复 → 重建；部署失败 → 切换备用环境 |

**Phase 5内部流程：**

```
npm run build（或对应的构建命令）
    ↓ (成功)
部署到Cloudflare Pages Preview环境
    ↓ (成功)

    ↓ (成功)

    ↓ (完成)
准备就绪，通知PM可以开始验收
```

#### Phase 6: 引导式验收（详细设计见第8章）

| 项目 | 说明 |
|------|------|

| **输出** | 验收报告（每个功能的通过/失败/待修状态） |
| **PM参与度** | ~10%——PM看截图、答是否题 |
| **耗时** | 10-30分钟 |
| **自动化部分** | 截图生成、问题归类、AI修复、重新截图 |
| **PM操作部分** | 逐功能看截图 → 答是/否 → 不对时引导定位问题 |
| **失败场景** | 3轮修不好 → 自动升级处理方式 |

详细设计见第8章。

#### Phase 7: 一键上线

| 项目 | 说明 |
|------|------|

| **输出** | 可公开访问的生产URL |
| **PM参与度** | 1%——PM点"确认发布" |
| **耗时** | 2-3分钟 |
| **自动化部分** | 6项部署检查 → 生产部署 → 健康检查 → DNS更新 |
| **PM操作部分** | 点一个按钮 |
| **失败场景** | 部署失败 → 自动回滚 → 通知PM "部署遇到问题，已回滚，正在修复" |

**Phase 7内部流程：**

```

    ↓ (成功)

    ↓ (成功)

    ↓
PM看到："您的产品已上线！🌐 https://..."
```

| 返工循环 | 60分钟 | 离开+在场 | Phase 2-6部分重走 |
| Phase 7: 上线 | 3分钟 | **在场** | 发布成功 |
| **总计** | **153分钟** | PM参与70分钟 | |

#### 极端场景上限

| 场景 | 总耗时 | 触发条件 |
|------|--------|---------|
| 需求频繁变更 | 可达175分钟 | PM在验收时改了3个以上核心功能 |
| AI质量波动 | 可达180分钟 | AI模型当天响应质量下降，大量重试 |
| 熔断触发 | 中止 | 总时间超过全局超时（默认240分钟），系统暂停并报告 |

### 3.4 熔断机制与降级策略

全自动化流水线必须有"刹车"——当AI陷入无限修复循环或成本失控时，系统需要自动暂停。

#### 熔断触发条件

| 编号 | 熔断条件 | 触发后行为 | PM看到的 |
|------|---------|-----------|---------|
| B1 | 单步骤连续失败达到上限 | 暂停当前Phase | "有一个问题需要您帮忙确认" |
| B2 | 总时间超过240分钟 | 暂停整个Pipeline | "项目生成时间较长，已暂停" |
| B3 | Token消耗超过预算 | 暂停并报告 | "AI调用费用即将达到预算上限" |
| B4 | 同一文件被修改超过10次 | 暂停该功能 | "这个功能的实现遇到困难" |
| B5 | 3个以上功能同时失败 | 暂停整个Pipeline | "多个功能遇到问题，建议调整方案" |

#### 每步骤的重试上限

| 步骤 | 最大重试次数 | 重试间策略 | 达到上限后 |
|------|------------|-----------|-----------|
| 代码生成（单节点） | 3次 | 第2次切换prompt策略，第3次切换AI模型 | 标记节点为error，跳过 |
| Lint/类型修复 | 3次 | AI读错误信息改代码 | 暂停，报告给PM |
| 安全修复 | 2次 | AI应用已知修复模式 | 标记漏洞，高危阻塞部署 |
| 测试修复（Layer 1） | 3次 | AI改代码或改测试 | 升级到Layer 2 |
| 测试修复（Layer 2） | 2次 | 使用不同AI+策略 | 升级到Layer 3 |
| 测试修复（Layer 3） | 1次 | — | 标记为"需PM验收确认" |
| 构建修复 | 3次 | AI分析build错误 | 暂停，报告给PM |
| 部署 | 2次 | 切换备用部署策略 | 自动回滚，报告给PM |

#### 降级策略链

当某个能力不可用时，系统自动降级而非完全中止：

```
正常模式
    ↓ (AI模型超时)
降级1: 切换到备用AI模型
    ↓ (备用也超时)
降级2: 使用更便宜但更快的模型（质量下降，标记"降级生成"）
    ↓ (全部模型不可用)
降级3: 暂停生成，已完成的功能可以预览
    ↓ (PM要求继续)
降级4: 队列等待，AI模型恢复后自动继续
```

```
正常测试（三层防线）
    ↓ (Layer 2的外部AI不可用)
降级1: 跳过Layer 2，Layer 1 + Layer 3
    ↓ (Layer 3也不可用)
降级2: 仅Layer 1，标记"测试覆盖降级"
    ↓ (所有测试基础设施不可用)
降级3: 跳过自动测试，标记"未测试"，强制进入PM验收
```

```
正常部署（Cloudflare Pages + Railway）
    ↓ (Cloudflare不可用)
降级1: 切换到Vercel
    ↓ (Vercel也不可用)
降级2: 本地WebContainer预览模式
    ↓ (WebContainer不可用)
降级3: 静态截图预览模式（PM看截图验收，无法交互）
```

#### 全局超时预算分配

总时间预算：240分钟（4小时）。按Phase分配如下：

| Phase | 时间预算 | 硬超时 | 超时后行为 |
|-------|---------|--------|-----------|
| Phase 1 | 不限制 | — | PM主导，不设超时 |
| Phase 2 | 30分钟 | 45分钟 | 未完成节点标记为error |
| Phase 3 | 10分钟 | 15分钟 | 跳过未通过的检查，标记 |
| Phase 4 | 30分钟 | 45分钟 | 降级测试覆盖 |
| Phase 5 | 5分钟 | 10分钟 | 切换备用部署方案 |
| Phase 6 | 不限制 | — | PM主导，不设超时 |
| Phase 7 | 10分钟 | 15分钟 | 自动回滚 |

## 4. 业务节点体系

### 4.1 7种业务节点类型

MIXIA Builder使用"业务节点"作为PM看到的功能单元。每种业务节点对应PM容易理解的业务概念，底层自动映射为技术实现节点（PM不可见）。

| 业务节点类型 | 图标 | PM视角说明 | 底层技术映射（PM不可见） |
|-------------|------|-----------|----------------------|
| **功能** (feature) | 拼图块 | 一个用户可感知的功能点，如"用户注册"、"商品搜索" | 多个code_gen节点 + test节点 |
| **页面** (page) | 窗口 | 一个具体的UI页面，如"登录页"、"商品列表页" | React组件 + 路由配置 + CSS样式 |
| **流程** (flow) | 箭头环 | 跨页面的用户操作路径，如"注册→登录→首页"、"选品→加购→下单→支付" | 多个page节点 + API串联 + 状态管理 |
| **数据** (data) | 表格 | 一个业务数据实体，如"用户"、"订单"、"商品" | 数据库表 + ORM模型 + 数据迁移脚本 |
| **对接** (connect) | 插头 | 外部系统/服务接入，如"微信支付"、"短信通知"、"阿里云OSS" | API集成代码 + 配置 + Secret管理 |
| **规则** (rule) | 天平 | 业务逻辑规则，如"满100减20"、"超时未支付自动取消" | 后端逻辑 + 数据校验 + 定时任务 |
| **里程碑** (milestone) | 旗帜 | PM设定的交付检查点，如"核心功能完成"、"可以演示" | checkpoint节点的业务包装（自动暂停等PM确认） |

#### 节点命名规范

节点标签**必须**是PM需求原文中的短语，不允许使用技术术语：

| 正确（PM语言） | 错误（技术语言） |
|---------------|----------------|
| 用户注册 | UserRegistration |
| 商品搜索 | ProductSearchAPI |
| 微信支付 | WechatPayIntegration |
| 满减优惠 | DiscountCalculator |
| 订单列表页 | OrderListComponent |

#### 每种节点类型的详细说明

**功能节点（feature）—— 最常用**

功能节点是PM在功能地图上最常看到的节点类型。一个功能节点代表一个用户可以感知和使用的完整功能。

示例：
```
功能: 用户注册
├── 说明: 新用户通过手机号注册账号
├── 包含:
│   ├── 注册页面（UI）
│   ├── 手机号验证码发送（后端API）
│   ├── 用户信息存储（数据库）
│   └── 注册成功跳转（前端逻辑）
├── 依赖: 无（独立功能）
└── 被依赖: 用户登录、个人中心
```

**页面节点（page）—— UI可视化**

页面节点代表一个具体的UI页面。在验收阶段，PM主要通过页面节点的截图来确认UI是否正确。

示例：
```
页面: 商品详情页
├── 说明: 展示单个商品的详细信息
├── 包含:
│   ├── 商品图片轮播
│   ├── 价格和规格选择
│   ├── 加入购物车按钮
│   └── 商品评价列表
├── 依赖: 商品数据（data节点）
└── 被依赖: 购物车流程（flow节点）
```

**流程节点（flow）—— 跨页面路径**

流程节点代表一个跨越多个页面的完整用户操作路径。它是多个页面节点和功能节点的串联。

示例：
```
流程: 下单支付流程
├── 说明: 从选择商品到完成支付的完整路径
├── 步骤:
│   ├── 1. 商品详情页 → 点击"立即购买"
│   ├── 2. 确认订单页 → 填写收货地址
│   ├── 3. 选择支付方式 → 跳转支付
│   ├── 4. 支付成功 → 跳转订单详情
│   └── 5. 订单详情页 → 查看物流
├── 依赖: 商品详情页、购物车、微信支付、用户地址
└── 被依赖: 评价功能
```

**数据节点（data）—— 业务实体**

数据节点代表一个核心业务数据实体。PM通过数据节点理解系统管理了哪些数据。

示例：
```
数据: 订单
├── 说明: 用户的购买订单
├── 字段:
│   ├── 订单号（自动生成）
│   ├── 买家信息
│   ├── 商品列表
│   ├── 总金额
│   ├── 收货地址
│   ├── 支付状态
│   └── 创建时间
├── 依赖: 用户（data）、商品（data）
└── 被依赖: 支付流程、订单管理
```

**对接节点（connect）—— 外部服务**

对接节点代表与外部系统或服务的接入。这类节点通常涉及第三方API密钥和配置。

示例：
```
对接: 微信支付
├── 说明: 接入微信支付，支持用户在线付款
├── 需要PM提供:
│   ├── 微信商户号
│   ├── API密钥
│   └── 回调域名
├── 预览模式: 使用微信支付沙箱（不产生真实扣款）
└── 被依赖: 下单支付流程
```

**规则节点（rule）—— 业务逻辑**

规则节点代表一条业务规则或逻辑。这类节点特别需要PM在验收时仔细检查。

示例：
```
规则: 满减优惠
├── 说明: 订单满100元减20元
├── 规则详情:
│   ├── 条件: 订单商品总额 >= 100元
│   ├── 动作: 减免20元
│   ├── 叠加: 不与其他优惠叠加
│   └── 时效: 长期有效
├── 依赖: 订单数据、商品数据
└── 被依赖: 下单流程、订单金额计算
```

**里程碑节点（milestone）—— 检查点**

里程碑节点是PM在功能地图上设定的检查点。当Pipeline执行到里程碑时，系统自动暂停并通知PM确认。

示例：
```
里程碑: 核心功能完成
├── 说明: 注册、登录、商品浏览、下单支付全部完成
├── 包含的功能: 用户注册、用户登录、商品列表、商品详情、下单支付
├── 到达条件: 以上所有功能状态为"已确认"
└── 到达后: 暂停Pipeline，通知PM预览确认
```

### 4.2 业务状态机（8种状态）

每个业务节点有8种可能的状态。PM通过颜色和图标一眼看出每个功能的进度，以及现在该做什么。

| 状态 | 颜色 | 图标效果 | 含义 | 谁触发下一步 |
|------|------|---------|------|-------------|
| **待规划** | 灰色 | 静止 | AI尚未开始分析这个功能 | 自动（等前置功能完成） |
| **方案中** | 蓝色 | 静止 | AI正在为这个功能生成方案 | 自动 |
| **待确认** | 橙色 | 脉冲闪烁 | 方案已出，等PM确认 | **等PM操作** |
| **开发中** | 蓝色 | 旋转动画 | PM已确认，AI正在生成代码+测试 | 自动 |
| **可预览** | 紫色 | 脉冲闪烁 | 代码已生成+测试通过+已部署预览，等PM验收 | **等PM操作** |
| **需修改** | 红色 | 静止 | PM反馈了修改意见，AI正在修复 | 自动（AI修复中） |
| **已确认** | 绿色 | 勾号 | PM确认功能OK | **PM触发**（验收通过） |
| **已上线** | 深绿色 | 火箭图标 | 已部署到生产环境 | **PM触发**（点"发布"） |

**关键设计：脉冲/闪烁 = "轮到PM操作了"**

PM打开页面后，一眼就能看出哪些功能需要自己操作（橙色脉冲/紫色脉冲），哪些AI还在处理（蓝色旋转），哪些已经搞定（绿色勾号）。

#### 状态转换规则

```
待规划 ──→ 方案中 ──→ 待确认 ──→ 开发中 ──→ 可预览 ──→ 已确认 ──→ 已上线
  │                     │                      │          │
  │                     ↓                      ↓          │
  │                   (PM修改方案)            (PM说"不对") │
  │                     │                      │          │
  │                     ↓                      ↓          │
  │                   方案中                  需修改       │
  │                  (重新生成)              (AI修复)      │
  │                                           │          │
  │                                           ↓          │
  │                                         可预览       │
  │                                        (修复后再验)   │
  └──────────────────────────────────────────────────────┘
```

**状态转换的触发者：**

| 转换 | 触发者 | 条件 |
|------|--------|------|
| 待规划 → 方案中 | 系统自动 | 前置依赖的功能已到"待确认"或更后的状态 |
| 方案中 → 待确认 | 系统自动 | AI完成方案生成 |
| 待确认 → 开发中 | **PM** | PM确认方案（I2中点"确认"） |
| 待确认 → 方案中 | **PM** | PM修改方案（I2中点"这里不对"） |
| 开发中 → 可预览 | 系统自动 | 代码生成+质量检查+测试+预览部署全部完成 |
| 可预览 → 已确认 | **PM** | PM在验收中确认功能OK |
| 可预览 → 需修改 | **PM** | PM在验收中说"不对" |
| 需修改 → 可预览 | 系统自动 | AI修复完成+重新通过测试+重新部署预览 |
| 已确认 → 已上线 | **PM** | PM点"确认发布"（I5） |

#### 底层技术状态（PM不可见）

每个业务状态的背后，有更细粒度的技术状态在运行。PM不需要看到这些，但系统内部使用：

| 业务状态 | 底层技术状态 |
|---------|-------------|
| 待规划 | `pending` |
| 方案中 | `analyzing` → `planning` |
| 待确认 | `plan_ready` |
| 开发中 | `generating` → `completed` → `linting` → `testing` → `deploying_preview` |
| 可预览 | `preview_ready` |
| 需修改 | `fix_analyzing` → `fix_generating` → `fix_testing` → `fix_deploying` |
| 已确认 | `approved` |
| 已上线 | `production_deployed` |

状态派生规则（技术状态如何映射为业务状态）的完整定义见第5章。

#### 视图切换设计

三个视图之间通过顶部图标按钮一键切换，类似Notion的视图切换：

- **功能地图**：适合"全局理解"——我的产品有哪些功能、怎么关联
- **看板**：适合"进度跟踪"——哪些在做、哪些等我、哪些完成了
- **用户旅程**：适合"业务走查"——用户从头到尾怎么用这个产品

三个视图的数据是同一份（同一组业务节点），只是展示角度不同。在任何视图中修改节点状态，其他视图同步更新。

### 4.4 业务节点到技术节点的映射关系

每个PM看到的"业务节点"在底层对应1到多个"技术节点"。这种映射是自动的、PM不可见的。以下是映射关系的完整定义：

#### 映射规则

| 业务节点类型 | 底层技术节点组成 | 典型数量 |
|-------------|----------------|---------|
| **功能** (feature) | code_gen(前端) + code_gen(后端) + code_gen(API) + test(单元) + test(集成) | 3-6个 |
| **页面** (page) | code_gen(React组件) + code_gen(路由配置) + code_gen(样式) + test(组件测试) | 3-5个 |
| **流程** (flow) | 多个page技术节点 + code_gen(状态管理) + code_gen(API串联) + test(E2E) | 5-10个 |
| **数据** (data) | schema_design(DDL) + code_gen(ORM模型) + code_gen(数据迁移) + code_gen(CRUD API) + test | 4-6个 |
| **对接** (connect) | code_gen(API集成) + config(环境变量) + code_gen(错误处理) + test(Mock测试) | 3-5个 |
| **规则** (rule) | code_gen(业务逻辑) + code_gen(数据校验) + test(边界测试) | 2-4个 |
| **里程碑** (milestone) | checkpoint(暂停等确认) | 1个 |

#### 业务状态的派生规则

业务节点的状态由其底层所有技术节点的状态综合得出：

| 业务状态 | 底层技术节点条件 |
|---------|----------------|
| 待规划 | 所有技术节点都是 `pending` |
| 方案中 | 至少1个技术节点是 `analyzing`/`planning` |
| 待确认 | 所有技术节点的方案已生成，等待PM确认 |
| 开发中 | 至少1个技术节点是 `generating`/`completed`/`linting`/`testing` |
| 可预览 | 所有技术节点都通过了验证和测试，预览部署完成 |
| 需修改 | 至少1个技术节点是 `fix_*` 状态 |
| 已确认 | 所有技术节点都是 `approved` |
| 已上线 | 所有技术节点都是 `production_deployed` |

**特殊规则：**
- 如果底层有1个技术节点失败（error），但其他都成功，业务状态显示为"开发中"（AI正在修复），不直接暴露error给PM
- 只有当修复也失败（达到重试上限）时，业务状态才变为"需修改"，并翻译为PM能理解的问题描述

#### 共享技术节点的处理

多个业务节点可能共享底层的技术节点。例如：

```
业务节点"用户注册"  ──→  schema_design: users表
业务节点"用户登录"  ──→  (共享) ↑
业务节点"个人中心"  ──→  (共享) ↑
```

`users` 数据库表被3个业务功能共享。处理规则：
- 删除"用户注册"业务节点时，`users`表的技术节点**不会**被删除（因为其他功能还在用）
- 修改"用户注册"导致`users`表结构变化时，系统自动分析"用户登录"和"个人中心"是否受影响
- 受影响的业务节点自动标记为"需修改"

#### 映射的自动生成

PM不需要手动定义映射关系。AI在Phase 1（需求理解）时自动完成以下工作：

1. 解析PM的业务需求 → 识别业务节点
2. 为每个业务节点自动规划底层技术节点
3. 识别技术节点间的依赖关系和共享关系
4. 生成完整的双层节点图（PM只看到业务层）

PM在I2（方案确认）时看到的功能地图就是业务层的投影。底层技术层的一切对PM透明，除非出现需要PM决策的情况（如共享冲突、影响范围过大等）。
